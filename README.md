KAVIK TASKMANAGEMENT — ОТЧЁТ ПО ТЕСТИРОВАНИЮ И КОД-РЕВЬЮ MVP
============================================================

Дата: 19.10.2026

ИТОГ
----

MVP функционально готов к показу, но не к работе с реальными данными. Сценарии от входа до автоматизаций работают, матрица ролей и защита от доступа к чужим данным (IDOR) выдержали все проверки. XSS и SQL-инъекций нет, SSRF закрыт, известных CVE в зависимостях нет. Бэкенд: 479 тестов зелёные, покрытие 87%. Фронтенд: 185 тестов, 70,7%.

До использования нужно закрыть критичные проблемы (K-1…K-5):

1. Ветка main собирается в белый экран. Фикс clientId.ts лежит в рабочей копии незакоммиченным, а стенд собран из неё, а не из коммита 4a9ce4e. Срочно закоммитить фикс (K-1).
2. Стенд на голом IP по HTTP. Порт 8380 открыт в интернет без firewall. Пароль и токены идут открытым текстом. Refresh-cookie уходит на соседние сервисы этого IP: :80, :8000, :8090, :5173. Нужен HTTPS через Caddy с sslip.io (K-2, K-3).
3. Демо-администратор с общим паролем на публичном стенде. У 15 демо-аккаунтов один пароль (K-4).
4. Одна карточка со сроком 0001-01-01 останавливает напоминания о сроках во всей организации. Поставить такой срок может любой, кто редактирует карточки (K-5).

Дальше по важности: сортировка приоритета в «Моих задачах» (В-1), отсутствие таймаутов Redis (В-2), двойная отправка форм колонок и досок (В-3), повтор запроса от чужого аккаунта после refresh (В-4), отсутствие экрана ошибки после передеплоя (В-5).

Побочные эффекты проверки. Код и конфиги не менялись. На стенде остались 7 заблокированных тестовых пользователей qa-*@example.com: API не умеет удалять пользователей. Остальные тестовые сущности удалены. Напоминания о сроках не работали около 75 секунд во время проверки K-5. При прогоне проверок перезаписан кэш frontend/node_modules/.tmp/*.tsbuildinfo: это вне git, содержимое равнозначно результату npm run typecheck.

ПРОЕКТ И АРХИТЕКТУРА
--------------------

TaskManagement — внутренний аналог Kaiten для blackout. В нём есть организация с отделами, пространства с ролями, канбан-доски с колонками и дорожками, карточки (чек-листы, подзадачи, комментарии с упоминаниями, история), realtime через WebSocket, «Мои задачи», поиск, уведомления, Telegram-бот и конструктор автоматизаций «когда → если → то». Разработка шла в 8 этапов с 12 по 15.10, PR #1–#8 влиты в main, всего 20 коммитов.

Схема: Браузер -> (HTTP, 0.0.0.0:8380) -> web (nginx 1.31.7: статика SPA, прокси /api, /api/ws, /health) -> api (FastAPI: REST + WebSocket, JWT).
api -> PostgreSQL 17 (данные, 13 миграций) и Redis 7 (refresh-токены, pub/sub, очередь).
scheduler (taskiq, проверка сроков по минутам) -> очередь Redis -> worker (taskiq: правила автоматизаций, доставка в Telegram) -> внешние URL (HTTP-действия правил) и Telegram (бот не запущен).
Наружу опубликован только web на 8380 без TLS и firewall; остальные контейнеры только во внутренней сети Docker.

Стек. Бэкенд: Python 3.12, FastAPI, SQLAlchemy 2 (async), asyncpg, Alembic, Redis, taskiq, PyJWT, Argon2 (pwdlib); сборка через uv, ruff, mypy strict, pytest. Фронтенд: Vite, React 19, TypeScript, Ant Design 6, React Router 8, TanStack Query, dnd-kit; vitest, ESLint. Размер: около 26,6 тыс. строк, 109 Python-файлов в backend/app и 156 TS-файлов в frontend/src.

Запуск. Docker Compose проект kavik-tm: контейнеры db, redis, api, worker, scheduler, web; одноразовый migrate применяет миграции и создаёт организацию с владельцем. Сервис bot на стенде не запущен: токен Telegram не задан. Systemd и внешний прокси не используются. Внешние сервисы: Telegram Bot API и произвольные URL из HTTP-действий автоматизаций.

ЖУРНАЛ НАХОДОК
--------------

В журнале 54 находки: 5 критичных, 12 важных и 37 мелких. В скобках указано, чем подтверждена находка: «стенд» — воспроизведена на :8380, «тест» — проверочным тестом, «код» — только чтением кода. Пути даны относительно /srv/kavik/TaskManagement, секреты замаскированы.

Критичные:

K-1. Баг: main собирается в белый экран при открытии по HTTP (тест).

- Где: frontend/src/api/clientId.ts:8 в коммите 4a9ce4e, вызов crypto.randomUUID() на уровне модуля.
- Факт: по HTTP на IP контекст не защищённый, и randomUUID в браузере нет. Модуль падает, страница остаётся белой. login.png в корне репозитория — снимок этого экрана. Стенд работает только потому, что собран из рабочей копии с незакоммиченным фиксом.
- Ожидание: сборка из main открывается.
- Как воспроизвести: собрать 4a9ce4e и открыть http://<ip>:8380.
- Как исправить: закоммитить изменения clientId.ts (генерация через crypto.getRandomValues, биты v4 выставлены верно) и clientId.test.ts. В stand.env поправить пометку «снимок коммита 4a9ce4e».

K-2. Уязвимость: стенд работает по HTTP без TLS (стенд).

- Где: tm-demo/docker-compose.stand.yml (8380:8080), в stand.env задано AUTH_COOKIE_SECURE=fal*.
- Факт: пароль при входе, access-токен (в том числе первым сообщением WebSocket) и refresh-cookie идут по интернету открытым текстом. У cookie нет флага Secure, HSTS невозможен.
- Как исправить: в системный Caddy добавить tm.157-245-67-89.sslip.io { reverse_proxy 127.0.0.1:8380 } по образцу hub. Публиковать порт как 127.0.0.1:8380:8080. Задать AUTH_COOKIE_SECURE=true и PUBLIC_BASE_URL=https://….

K-3. Уязвимость: refresh-cookie на голом IP получают все сервисы этого IP (код и конфигурация).

- Где: backend/app/api/routes/auth.py:152-161; cookie выставлена с Path=/api/auth и SameSite=Strict.
- Факт: браузер не разделяет cookie по портам. На 157.245.67.89 работают чужие сервисы: :80 (fbclone), :8000 (fbads), :8090 (hub), :5173 (node от root). Любой пользователь сервера может поднять свой порт. Страница на этом порту запросом на свой /api/auth/* получит refresh_token, а затем вызовет /api/auth/refresh на :8380. Итог — захват аккаунта на 14 дней.
- Как проверить: войти на :8380 и открыть http://157.245.67.89:8090/api/auth/x. В запросе будет заголовок Cookie: refresh_token=….
- Как исправить: отдельное имя хоста с HTTPS (K-2), Secure-cookie, по возможности префикс __Host-.

K-4. Уязвимость: демо-администратор с общим паролем на публичном стенде (код и БД стенда).

- Где: backend/app/demo.py:95,138, у maria@demo.example.com роль ADMIN; список демо-email есть в DOCUMENTATION.md:581. В DEMO_PASSWORD=dem* 15 символов, внутри словарное «demo».
- Факт: у 15 демо-аккаунтов один пароль, один из них — администратор организации. Узнавший пароль может сбрасывать пароли, блокировать пользователей и создавать HTTP-автоматизации. Лимит перебора — 50 неудач за 15 минут на аккаунт, то есть до \~4800 попыток в сутки на каждый из 15 аккаунтов (оценка).
- Как исправить: снять роль ADMIN с демо-пользователя или раздавать случайный пароль адресно; закрыть стенд basic-auth или списком IP; удалить демо-данные после показа.

K-5. Баг: одна карточка со сроком 0001-01-01 останавливает напоминания всей организации (стенд).

- Где: backend/app/services/due_reminders.py:42, выражение due_date - timedelta(days=1); схема CardUpdate в schemas/card.py:40 не ограничивает дату.
- Шаги: PATCH /api/cards/{id} с {"due_date":"0001-01-01"}, подождать минуту, открыть docker logs kavik-tm-worker-1.
- Факт: задача check_due падает с OverflowError: date value out of range и откатывается целиком. Пока такая карточка существует, во всей организации не работают напоминания «завтра срок» и «просрочено» и триггер due_reached. Хватает права редактировать карточки.
- Ожидание: 422 на нереальную дату, а одна карточка не ломает обработку остальных.
- Как исправить: ограничить due_date, например 2000–2100; в check_due обрабатывать каждую карточку в своём try/except.
